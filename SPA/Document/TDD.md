### 4.3 Initial Catalog Seed Contract

The implementation supplies a version-controlled seed manifest for the 11 services in Business Logic 7.1. Each variant includes:

- bilingual names, short customer descriptions, and category
- duration and integer `priceSatang`
- `pricingMode`: `PER_PARTICIPANT` or `PER_BOOKING`
- `requiredPax`: `1` or `2`
- resource requirements, active state, and display order
- `catalogVersion` and source metadata

`Couple Relaxation Package` is the only initial `PER_BOOKING` / `requiredPax=2` variant. Its 1,190 THB price is charged once, two participants reference the same Booking line item, and resources are allocated for both. `Hot Compress` is a standalone 20-minute variant in Phase 1. Seed import is idempotent by stable Service/Variant ID and never overwrites an Admin-edited record unless an explicit migration is approved.

Admin service creation accepts one or more unique duration/price variants in the same request. Every duration is a 15-minute increment from 15–480 minutes, price is a non-negative integer in satang, and all variants created for one service share its `pricingMode` and `requiredPax`. `POST /api/v1/admin/services/{serviceId}/variants` adds another duration to an existing service with `expectedVersion`; it rejects a duplicate duration and inherits the service's pricing and resource requirements.

## 6. API Conventions

### 6.1 Base Paths and Media Types

- Public API base: `/api/v1/public`
- Admin API base: `/api/v1/admin`
- LINE webhook base: `/api/v1/webhooks/line`
- Private worker base: `/internal/v1`
- Health endpoints: `/health/live` and `/health/ready`
- JSON media type: `application/json; charset=utf-8`
- Errors: `application/problem+json`
- API timestamps: RFC 3339 UTC, for example `2026-08-15T07:00:00Z`
- Local business dates: ISO `YYYY-MM-DD`
- Local business times: 24-hour `HH:mm`
- Currency: integer minor units named `amountSatang`; no floating-point prices

### 6.2 Request Context

Every request receives:

- `requestId`: accepted from a valid `X-Request-ID` or generated as UUID v4
- `correlationId`: propagated across API, outbox, task, worker, and provider attempt
- Caller type: `GUEST`, `LINE_CUSTOMER`, `ADMIN_USER`, `LINE_GROUP_MEMBER`, or `SERVICE`
- Environment and service revision in structured logs

Sensitive request bodies are not logged.

### 6.3 Pagination

Admin list APIs use opaque cursor pagination:

- `pageSize`: default 25, maximum 100
- `pageToken`: base64url-encoded, signed cursor state
- Response: `items`, `nextPageToken`, `hasMore`, and optional summary/estimate fields
- Admin Booking Queue orders by `startAt DESC, documentId DESC` so the newest appointment is always shown first; the signed cursor is bound to branch/date/status/search filters
- Booking status/search filters execute on the API, not against only the rows loaded in the browser; operational summary counts remain branch-wide and are not derived from the current page

Offset pagination is not used for Firestore operational lists.

### 6.4 Optimistic Concurrency

Mutable operational resources expose an integer `version`. Commands that can overwrite current values include `expectedVersion`. A stale version returns `409 RESOURCE_VERSION_CONFLICT`.

Booking state transitions also verify the current status inside a Firestore transaction. LINE confirmation does not require a client version because it is a compare-and-transition from `PENDING` only.

## 7. Authentication and Caller Verification

### 7.1 Website Guest

A Guest has no account and no persistent session. Availability browsing is anonymous. Booking submission requires:

- Valid reCAPTCHA assessment for action `booking_submit`
- Valid `Idempotency-Key`
- Phone and IP abuse checks
- Valid booking payload, Booking/Privacy acknowledgement, and explicit health-data consent for each participant

A phone number is contact data, not proof of identity. The system never exposes other bookings based only on a matching phone number.

### 7.2 LINE-linked Customer

Customer Web obtains a LINE ID token through LIFF/LINE Login and submits it only when identity is needed. The SPA API verifies the token server-side against the configured Customer LINE channel and validates audience, issuer, signature, expiry, and nonce where applicable.

The API derives the trusted LINE User ID from the verified token. It never trusts a client-provided User ID, display name, or profile object. No application customer JWT is issued in Phase 1.

### 7.2.1 Read-only Customer Booking List

`POST /api/v1/customer/bookings:list` accepts `lineIdToken`, `view` (`UPCOMING` or `HISTORY`), `pageSize` (maximum 50), and an optional signed `pageToken`. The API verifies the LINE token on each request and derives `SHA-256("LINE:" + channelId + ":" + lineUserId)`; raw LINE IDs and ID tokens are never query fields or response data.

The query filters `bookings.lineIdentityHash`, orders by `startAt` plus document ID, and classifies each result against one stable `asOf` timestamp for the complete paginated traversal. Upcoming contains future `PENDING`/`CONFIRMED` Bookings plus `IN_SERVICE`; History contains terminal statuses and past `PENDING`/`CONFIRMED` Bookings. Upcoming is ascending; History is descending. The API scans filtered records in bounded batches so stale operational statuses cannot leave past appointments in Upcoming. The signed base64url cursor is bound to the selected view and carries the signed `asOf` timestamp; it uses the existing Customer Messaging channel secret with the domain separator `customer-bookings:v1` as signing material. Responses contain only public Booking ID, status, local appointment, service-name snapshots, pax, estimated total, currency semantics, and `nextPageToken`.

### 7.3 Customer Profile Resolution

- A follow/unfollow webhook updates a pseudonymous `line_friendships` record. Following the OA alone does not create a Customer Profile or CRM record.
- A verified Customer LINE User ID resolves an existing `customer_identity_links` record or creates a new Customer Profile only when the customer explicitly submits a booking/campaign flow with the required acknowledgement/consent.
- Campaign eligibility prefers server-verified friendship evidence from webhook or an authorized Followers API sync. A campaign may explicitly permit a positive LIFF `getFriendship()` response as lower-assurance `CLIENT_ATTESTED` evidence for followers who predate webhook capture. This policy is disabled unless configured on that campaign.
- A Website Guest submission creates a provisional Customer/Participant Profile for that Booking. A phone match may be shown as a restricted staff-side reconciliation candidate but is never sufficient for automatic merge, login, or profile disclosure.
- `ADMIN` or `STAFF` may reconcile/merge profiles only after confirming the customer in an operational interaction. The merge records source/target IDs, actor, reason, time, and a safe field-change summary.
- The current Health Profile may prefill a future verified LINE booking after the customer is informed and can correct it. Every submit creates a separate Booking Health Snapshot.

### 7.4 Consent Evidence

The API recognizes independent versioned consent purposes:

| Purpose | Required | Evidence scope |
| --- | --- | --- |
| `BOOKING_PRIVACY_ACK` | Every submit | Booking/contact owner |
| `HEALTH_DATA_EXPLICIT` | Every participant whose declaration is collected, including “none” | Participant |
| `SECOND_PARTICIPANT_AUTHORIZATION` | When the contact submits data for participant 2 | Participant 2 and submitting contact |

Checkboxes are unchecked by default. Evidence stores wording version/hash, purpose, participant, capture channel, timestamp, actor/verified LINE link when present, and withdrawal state. Consent text is not bundled with any future marketing purpose. Withdrawal creates an audited privacy workflow; it does not silently destroy data needed for a documented legal hold.

### 7.5 Admin Web

- Firebase Google Sign-In is enabled; public sign-up does not grant application access.
- An `app_users` invitation must exist for the normalized email.
- The Admin Web sends the Firebase ID token as `Authorization: Bearer <token>`.
- The API verifies the token with the Firebase Admin SDK.
- The API loads `app_users/{firebaseUid}` and requires `active=true`.
- The Firestore role is authoritative: exactly `ADMIN` or `STAFF`.
- Mutation endpoints check token revocation where configured and always check the active application record.
- First successful invited login binds the invitation email to the Firebase UID atomically.

### 7.6 Internal Services

Cloud Tasks and Cloud Scheduler use OIDC tokens with dedicated service accounts and a worker-specific audience. The worker validates Cloud Run/IAM authentication and rejects traffic from all other principals.

### 7.7 LINE Webhooks

Each LINE endpoint validates `x-line-signature` against the raw request body and the correct environment/channel secret before parsing. Admin and Customer channel secrets are never interchangeable.

## 11. Identifier and Data Normalization Rules

| Value | Technical rule |
| --- | --- |
| Internal document ID | Firestore auto ID or UUID v4; never exposed as access authority |
| Public Booking ID | `BK-YYYYMMDD-NNN`, based on the branch-local appointment date at creation and an atomic date counter; it remains unchanged after reschedule |
| Idempotency key | Client-generated UUID v4; stored for 24 hours |
| Phone | Parse Thai local and E.164 input; persist canonical E.164 plus masked display form |
| Phone enforcement key | HMAC-SHA-256 of canonical phone using environment-specific pepper |
| IP enforcement key | HMAC-SHA-256 of canonical client IP using environment-specific pepper |
| Nickname | Unicode normalized, trimmed, 1–80 characters |
| Currency | Integer satang, non-negative |
| Duration | Positive whole minutes; customer-bookable variants must align to 15-minute buckets |
| Time | UTC timestamps plus branch-local date/time fields required for operational queries |

Public Booking ID sequence contention is acceptable at the approved volume. The Firestore document ID remains independent so a public ID cannot be used to infer a storage path. The date portion is a human reference snapshot, not the source of current appointment truth.

## 13. Capacity Bucket and Resource Model

### 13.1 Bucket Granularity

The canonical interval is 15 minutes. A resource reservation occupies every bucket from start inclusive to end plus configured buffer exclusive.

Example: a 90-minute service at 14:00 with a 15-minute buffer consumes `14:00` through `15:30` service time and the `15:30` buffer bucket, releasing at 15:45.

### 13.2 Service Requirements

Each active service variant defines one or more resource requirements:

- `resourceType`, for example `BED`, `ROOM`, or `AREA`
- `units` required per participant
- optional compatible resource IDs or tags
- whether the requirement is mandatory

A participant may consume multiple resource types simultaneously. Therapist capacity is excluded in Phase 1.

### 13.3 Deterministic Allocation

For every requirement:

1. Load active compatible resources for the branch.
2. Remove resources blocked during any required bucket.
3. Remove resources without sufficient units in every bucket.
4. Sort by configured allocation priority.
5. Prefer the candidate with the smallest remaining capacity after allocation.
6. Use stable Resource ID as final tie-breaker.
7. Backtrack across participants and requirement groups until a complete allocation is found.

With at most two participants, bounded backtracking remains predictable. Partial allocation is never committed.

## 14. Booking Creation Transaction

The creation operation has a pre-transaction validation stage and one Firestore transaction.

### 14.1 Pre-transaction

- Validate syntax and consent
- Normalize phone, nickname, times, and IDs
- Verify optional LINE token
- Verify Guest reCAPTCHA and abuse policy
- Load static catalogue/configuration needed to build candidate allocations
- Calculate payload digest and inspect idempotency record
- For Admin Staff-assisted creation, require an active `ADMIN`/`STAFF`, a 15-minute-aligned appointment, booking/privacy acknowledgement, and `VERBAL` or `PAPER` consent capture evidence
- Accept optional `discountAmountSatang` and `discountReason`; require whole-baht, non-negative input, require `ADMIN` and a non-empty reason when the amount is greater than zero, and require the discount to be less than the service subtotal
- Keep Coupon lookup/redeem independent. A reason such as `คูปองสมัครครั้งแรก` records why the Booking was discounted but never marks a coupon code redeemed implicitly
- `STAFF_ASSISTED` accepts the current non-past bucket or a future date and performs operating-hours, closure, duplicate, and capacity validation
- `HISTORICAL_RECORD` requires a past appointment time, commits `RECORDED`, preserves immutable subtotal/discount/net-service/tip/gross financial snapshots, and skips operating-hours/closure/capacity reservations, automatic payment/accounting creation, and notification outbox writes; non-historical creation rejects any positive tip
- Normalize the optional Admin-entered phone only when provided; never synthesize a placeholder number

### 14.2 Transaction

The transaction:

1. Re-reads branch, variant, resource, block, and relevant bucket versions.
2. Revalidates advance window and service/resource active states.
3. Confirms the complete allocation for all participants.
4. Reads and increments the branch-local appointment-date Booking counter.
5. Creates Customer Web/LIFF Bookings as `PENDING`; creates an authenticated active Admin Booking as `CONFIRMED`, or a historical record as `RECORDED`, with trusted actor timestamps in the same transaction. `RECORDED` permits only the audited correction to `CANCELLED`.
6. Creates immutable price-bearing Booking line items; a `PER_BOOKING` item is written and charged once. The Booking separately stores subtotal, Admin discount, and net estimated amount.
7. Creates participant and immutable Booking Health Snapshot documents linked to the appropriate line item.
8. Resolves or creates the verified/provisional Customer Profile, updates the current Health Profile, and writes versioned consent receipts.
9. Increments every capacity bucket.
10. Creates resource reservation documents.
11. Creates the Guest status-token digest document.
12. Creates optional verified LINE link.
13. Writes Booking-created audit and notification outbox events.
14. Stores the idempotent success response.

Phone abuse counters, active-`PENDING` phone limits, CAPTCHA and Guest status tokens apply only to public Guest submissions. An Admin-created record with a supplied phone still receives same-phone/same-time duplicate protection; a record without a phone stores `contact.mode=NONE` and cannot be automatically reconciled with a Customer Profile. Active Admin paths retain atomic capacity and closure checks; historical records explicitly do not consume or mutate capacity.

All reads occur before transaction writes. If contention causes a retry, allocation is recomputed from the newly read bucket values. If no complete allocation remains, the API returns `409 CAPACITY_UNAVAILABLE` and writes no Booking.

### 14.3 Post-commit

- Enqueue each new outbox event in Cloud Tasks.
- Return Booking ID, `PENDING`, customer-safe summary, and status token to Customer Web.
- Task enqueue failure is logged but does not fail or roll back the Booking; reconciliation recovers it.

## 15. Booking Modification and Capacity Release

### 15.1 Capacity-affecting Edit

Changing date, start time, variant, duration, pax, or buffer-sensitive configuration requires atomic reallocation:

1. Read the current Booking and all existing reservation/bucket documents.
2. Compute the complete new allocation.
3. Verify new capacity without releasing the old allocation first.
4. In one transaction, decrement old buckets, increment new buckets, replace reservations, update snapshots/version, and write audit/outbox.

If new capacity is unavailable, no old capacity is released and the Booking remains unchanged.

### 15.2 Cancellation and Terminal States

`CANCELLED`, `COMPLETED`, `NO_SHOW`, and `RECORDED` do not consume capacity. Active Booking transitions decrement every active reservation bucket exactly once and mark reservation documents released. `RECORDED → CANCELLED` has no reservation to release and must not read or mutate Capacity. Repeated transitions cannot decrement again.

`IN_SERVICE` continues consuming capacity until `COMPLETED`.

### 15.3 Capacity Configuration Change

Reducing resource capacity or adding a block never auto-cancels an existing Booking. If current usage exceeds new configuration, the API records an operational conflict surfaced in Admin Web and prevents additional allocation.

## 16. State Transition Enforcement

| From | Command | To | Additional condition |
| --- | --- | --- | --- |
| `PENDING` | Confirm | `CONFIRMED` | Admin Web permission or valid registered group approver |
| `PENDING` | Cancel | `CANCELLED` | Reason required |
| `CONFIRMED` | Start | `IN_SERVICE` | Every participant has an active therapist assignment |
| `CONFIRMED` | Cancel | `CANCELLED` | Reason required |
| `CONFIRMED` | No-show | `NO_SHOW` | Appointment has reached the operational no-show window |
| `IN_SERVICE` | Complete | `COMPLETED` | Authorized Admin Web user |
| `RECORDED` | Cancel | `CANCELLED` | Reason required; set `financiallyExcluded=true`; no Capacity or notification write |

`COMPLETED`, `CANCELLED`, and `NO_SHOW` cannot be reopened in Phase 1 through ordinary endpoints. `RECORDED` supports only the reason-required correction to `CANCELLED`; no other transition is valid.

## 18. Guest Secure Status Link

### 18.1 Token Design

- Generate 32 cryptographically secure random bytes.
- Encode as unpadded base64url.
- Store only `SHA-256(token)` as the lookup key.
- Return the raw token once in the Booking response.
- Customer Web constructs `https://<booking-host>/status#t=<token>`.
- Because the token is in the URL fragment, browsers do not send it in HTTP paths, referrers, or default server access logs.
- Customer Web submits the token in a POST body to `booking-status:resolve`.

### 18.2 Lifecycle

- Default expiry: seven days after the scheduled service end.
- On reschedule, extend expiry to seven days after the new service end.
- On early cancellation, retain access for seven days after cancellation.
- Admin Web may revoke and issue a replacement token.
- Resolution returns masked phone, no health detail, no internal IDs, and no therapist detail.
- Five failed resolutions per enforcement key in 15 minutes trigger temporary throttling.

A successful `POST /api/v1/public/booking-line-links` transaction also writes the channel-scoped `lineIdentityHash` and derived `customerListBucket` to the Booking. This makes an older Guest Booking visible in `/my-bookings` without using phone matching. Existing verified links are migrated by the dry-run-first `backfill_customer_booking_index.py` tool.

## 20. Notification Outbox and Cloud Tasks

### 20.1 Outbox States

```text
PENDING -> ENQUEUED -> PROCESSING -> SENT
                         |     ^
                         v     |
                     RETRYABLE-+
                         |
                         +-> FAILED
```

Each event contains a template type and data references, not health detail. The Worker uses a customer-safe projection for customer delivery and an explicit Admin Group projection that joins participant health snapshots only when the resolved destination is the configured registered Admin Group.

### 20.2 Queue Configuration

| Setting | Initial production value |
| --- | --- |
| Queue | `spa-line-notifications` |
| Region | `asia-southeast1` |
| Max dispatch rate | 10 tasks/second |
| Max concurrent dispatches | 20 |
| Max attempts | 8 including first attempt |
| Minimum backoff | 10 seconds |
| Maximum backoff | 1 hour |
| Maximum doublings | 5 |
| Maximum retry duration | 24 hours |
| Dispatch deadline | 30 seconds |

The worker returns `2xx` only after reaching a durable terminal/accepted state. Retryable provider or infrastructure errors return non-`2xx`. Permanent provider errors are recorded as `FAILED` and acknowledged with `2xx` to stop queue retry.

### 20.3 Claim and Reconciliation

- Processing lease: two minutes
- Reconciliation schedule: every five minutes
- Reconciliation batch: up to 100 events
- Reconcile `PENDING` older than one minute, `ENQUEUED` with no task evidence, eligible `RETRYABLE`, and expired `PROCESSING` leases
- Stop retry and mark `FAILED` when the event reaches eight attempts or 24 hours from the first attempt
- Use task names derived from event ID plus `enqueueGeneration`; retrying the same enqueue generation is deterministic while a recovered enqueue uses the next generation
- Worker delivery remains idempotent even when Cloud Tasks redelivers

## 21. Idempotency

### 21.1 Booking Submission

- Require `Idempotency-Key` UUID v4.
- Scope by endpoint and caller fingerprint, not only raw key.
- Store canonical payload SHA-256.
- Same key and same digest returns the original status and response.
- Same key and different digest returns `409 IDEMPOTENCY_CONFLICT`.
- Retain successful and deterministic failure records for 24 hours.
- Do not persist provider or internal transient `5xx` responses as final results.

### 21.2 Webhooks and Tasks

- LINE webhook events are deduplicated by `webhookEventId`; fallback key uses channel, source, timestamp, and message ID.
- Outbox event ID is the business-event idempotency key.
- The event carries a stable UUID used as LINE `X-Line-Retry-Key` for every push retry within the 24-hour delivery window.
- LINE `409` with an accepted-request identifier for that retry key is treated as accepted delivery, not failure.
- Notification attempt number is monotonic.
- Booking transition audit uses a unique command ID to prevent duplicated side effects.
